# Homepage create-with-prompt reuses the existing prompt-handoff hook in useAppData, rewired from the dead EE `ai` slice to the real aiBuilderStore

Ticket #9 asks for: type a prompt on the homepage → a new empty App is created → the builder opens with that prompt already sent as the first message. `HomePage.jsx`'s `createApp(appName, type, prompt, taggedResources)` already does the first half — it was built (for an unrelated EE/cloud "AI onboarding" cookie flow, `handleAiOnboarding`) to create the app and `navigate(...)` into it with `state: { prompt, taggedResources }` — and `AppBuilder/_hooks/useAppData.js` already has a matching `if (state?.prompt && !promptSentRef.current && ...)` block that opens the AI sidebar and sends the prompt as the first message on load. This is exactly ticket #9's shape, already wired end to end — just pointed at the wrong store.

That existing block reads `useStore((state) => state.ai?.sendMessage)` — the main App Builder store's `ai` slice, created via `getEditionSpecificSlice('createAiSlice')`, which resolves to `() => ({})` for `edition === 'ce'` (`getEditionSpecificSlice.js`). `state.ai` is therefore always `undefined` in this CE fork; every use of it in `useAppData.js` is guarded (`if (setConversation && setDocsConversation)`) except the `sendMessage(...)` call itself, which isn't — it's simply never reached today because nothing in CE sets `state.prompt` on navigation except the cloud-only onboarding cookie path this ticket doesn't touch. Wiring `CreateAppWithPrompt` to `createApp(name, undefined, prompt)` makes this the common path, so the dead call becomes reachable and would throw (`sendMessage is not a function`) on every homepage-prompt app creation.

Decided: rewire that one call site in `useAppData.js` to the real `aiBuilderStore` (built in tickets #4–8, the store `AiBuilderChatPanel` actually reads from) instead of building a second, parallel handoff mechanism inside the chat panel component. Reusing the existing hook is architecturally necessary, not just convenient: `AiBuilderChatPanel` only mounts once the AI sidebar is opened, so nothing inside the panel component itself can be the trigger that opens the sidebar and kicks off the send on first load — something at the app-load level has to do both, and `useAppData.js`'s existing block already does, with the right guards (`promptSentRef` against StrictMode double-invoke, clearing `state.prompt` from `history.state` so a refresh doesn't resend). The replacement calls `aiBuilderStore.getState().createConversation({ appId, conversationType: 'generate', handoff: true })` then `.sendMessage({ appId, content: state.prompt })` — `handoff: true` satisfies the acceptance criterion directly (`createNewConversation` already records it on the conversation's metadata; nothing else needs to change for that flag to exist).

Three pieces of the original block are dropped, not adapted: `appData.ai_conversation`/`taggedResources`/`moduleId` are EE-only fields our CE backend never sets (grepped `server/src/modules/apps/` for `ai_conversation` — no hits outside `ai_conversation_message`/`_learn`), so checking or threading them through is dead weight, not a real guard. The `if (setConversation && setDocsConversation) {...}` block just above stays untouched — it's already correctly no-op-guarded in CE and isn't part of this ticket's path. And the original's second guard clause — `(conversation?.aiConversationMessages || []).length === 0 && (liveMessages || []).length === 0` — is dropped too, not just rewired: `aiBuilderStore` is a global singleton, so reading its current `messages` here to decide "has this already been sent" would misfire if the user had a *different* app's AI chat open earlier in the same SPA session (its leftover messages would read as "already sent," silently skipping the send for the new app). `promptSentRef` — a ref scoped to this one hook instance, reset fresh on every app-builder mount — is the correct one-shot gate on its own; the extra store check in the original was already vacuous in CE anyway (`state.ai` being `{}` made both halves of it always empty).

**A second race, caught in review**: `useAppData.js`'s handoff and `AiBuilderChatPanel`'s own mount effect both key off the same trigger — `setSelectedSidebarItem('tooljetai')` + `toggleLeftSidebar(true)` mounts the panel, whose `useEffect([appId])` unconditionally runs `listConversations(appId).then(active ? loadConversation(active.id) : fetchZeroState())`. On a realistic fraction of runs (not a rare edge case — both fire within a few ms of each other on every single handoff), the panel's `listConversations` GET lands after the handoff's `createConversation` POST has already created the conversation, so `loadConversation` fires — and its success handler unconditionally overwrites `messages`/`currentConversationId` and nulls `streamingMessage` from a fresh `GET /ai/conversation/:id`, racing the handoff's own `sendMessage` optimistic push and SSE stream. This can wipe the just-sent prompt bubble or the accumulating streamed reply, directly contradicting "prompt appears... already in flight" for a real fraction of homepage handoffs, not just a cosmetic flicker.

Fixed with a one-shot store flag, `aiBuilderStore.skipConversationBootstrap`: `useAppData.js` sets it via `useAiBuilderStore.setState({ skipConversationBootstrap: true })` *synchronously*, before `toggleLeftSidebar(true)` mounts the panel — so it's already `true` on the panel's very first render. The panel's mount effect checks and consumes it (`if (skipConversationBootstrap) { setState({ skipConversationBootstrap: false }); return; }`) before ever calling `listConversations`, standing down entirely for that one mount since the handoff is already populating the store itself. Any *other* mount of the panel (switching apps, reopening the sidebar later) finds the flag `false` and bootstraps normally, unaffected.

**Scope**: only `CreateAppWithPrompt` (already wired into `HomePage.jsx` with a live `createApp` prop) is implemented. `GetStarted/HomePagePromptSection.jsx` — a second, still-fully-stubbed "create with prompt" entry point on the separate first-run onboarding screen — has no `createApp`-equivalent wired to it at all yet; giving it one is a distinct plumbing task with no shared code to reuse here, deferred until a ticket actually asks for that surface.
