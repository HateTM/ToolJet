# The homepage-prompt handoff is a status the panel reads, not a one-shot skip flag — and a lost prompt goes back to the composer

ADR-0010 stopped the homepage handoff from racing `AiBuilderChatPanel`'s own bootstrap with a boolean, `aiBuilderStore.skipConversationBootstrap`: `useAppData.js` sets it synchronously before opening the sidebar, and the panel's mount effect consumes it and returns before calling `listConversations`. That is correct while the handoff is working. It is wrong the moment the handoff fails, and #25 is the bill for that.

A boolean can only say "someone else is handling this mount". It cannot say whether that someone succeeded. So on a failed handoff the panel consumed the flag, returned, and — because the effect only re-runs on `appId`/`conversationType` change — never bootstrapped again for the rest of the app session: no conversation list, no zero-state, just the generic `{error}` banner over an empty panel. Meanwhile `useAppData.js` stripped `prompt` from `window.history.state` unconditionally, immediately after firing the async chain, so the text the user typed on the homepage was gone too. The two compounded into "retype it and start over", with a full page reload as the only other way out.

Decided: replace the boolean with `handoffStatus: 'idle' | 'pending' | 'succeeded' | 'failed'`, plus `handoffPrompt` holding the in-flight text. The panel's mount effect stands down for `'pending'` and `'succeeded'` and falls through to its normal bootstrap otherwise, with `handoffStatus` added to the effect's deps — so the transition to `'failed'` is itself what re-runs the bootstrap that the pending mount skipped. `'succeeded'` still skips, which is ADR-0010's race fix intact: the handoff populated the store, and re-reading the thread over it would clobber the streaming reply. On failure the panel prefills its composer from `handoffPrompt` (read-and-clear, so it can't clobber a later edit), and its bootstrap re-reads the conversation the handoff created if there is one: `createConversation` may well have succeeded and only the message failed, leaving the store pointed at a real thread whose only local content is `sendMessage`'s optimistic user bubble, which was never confirmed. Re-reading replaces that with what the server actually stored.

`window.history.state` keeps ADR-0010's unconditional strip, moved to run the moment `beginHandoff` has the prompt. Recovery reads the prompt from the store, not from navigation state, so nothing is lost by clearing it early — and the alternative is worse than it looks: a user who recovers the draft, edits it and sends it successfully would still have the original sitting in navigation state, and their next refresh would silently create a second conversation and send it again.

**Every read of the status is scoped to the app it was recorded for**, via a third field, `handoffAppId`. ADR-0010's boolean was safe to leave global because the first mount that saw it consumed it; a status has no such moment. This store is a module singleton that outlives any one app, so an unscoped `'succeeded'` would keep telling the panel to stand down after an SPA switch to a different app: that app's threads would never load, and the previous app's conversation would sit in the panel instead. Scoping it also keeps a failed handoff's recovered prompt out of a different app's composer.

The same "a status is never consumed" problem decides which actions clear it. `setConversationType` does, because a mode switch throws away the very thread the handoff produced — leaving the gate shut with an empty store would strand both modes. `resetConversation` deliberately does *not*: it is the panel's own "New chat", which starts an empty thread and fetches its own zero state, and since the bootstrap effect now watches `handoffStatus`/`handoffAppId`, clearing them there would re-run the bootstrap and reload the thread the user just cleared — something ADR-0010's self-consuming boolean never did. A spent handoff left in place is harmless: both terminal states are scoped to `handoffAppId`, and `'failed'` only ever *permits* a bootstrap, by which point its prompt has already been consumed.

**The read actions stopped dismissing errors.** `listConversations`, `loadConversation` and `fetchZeroState` each nulled `error` on start. That was invisible until the fallback above existed — it is built out of exactly those three calls, so triggering it erased the banner explaining why the prompt had just been handed back, leaving the user with an unexplained draft in the composer. A background read is not an answer to a failed write; `error` is now cleared only by a write that replaces it, an explicit `clearError`, a mode switch, or a new chat.

**`sendMessage` had to start reporting delivery.** The failure path it needed to catch was partly unreachable: `aiBuilderStore.sendMessage` swallows its own errors into `state.error` and resolves, so `createConversation(...).then(() => sendMessage(...)).catch(...)` only ever saw `createConversation` rejecting — a failed *message* ran the success branch, marking the handoff delivered and stripping the prompt. It can't simply throw instead: the chat panel calls it as a fire-and-forget click handler with no `.catch()`, so rejecting would surface as an unhandled rejection on every failed send in normal in-builder use. It now resolves to a boolean, and the handoff branches on that. A resolved request is not enough to call it delivered — an `error` SSE event ends the request normally after the backend gave up mid-stream — so the return value reads the error state recorded during that send, not the promise alone.

**Not chosen: don't set the flag until the handoff succeeds.** That inverts ADR-0010's whole reason for existing. The flag has to be true *before* the panel's first render, which happens within milliseconds of the sidebar opening and long before any network call resolves; setting it on success would leave the race it exists to close wide open for exactly the window that matters.
