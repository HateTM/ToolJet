# ADR-0047: Workflows fully implemented in CE — no edition or license gating, EE dist as read-only reference

Date: 2026-09-02
Ticket: none (fork work packages WP-0…WP-8)
Status: Accepted

## Context

The fork runs Community Edition by design (`server/ee/` and `frontend/ee/` are empty submodules; edition checked via `server/src/helpers/edition.helper.ts`). Workflows — workflow apps, the node-graph editor, a server-side execution engine, manual and webhook triggers, run history, the AI agent node, and the Python executor — are an EE feature upstream. However, the CE scaffolding for most of the backend already ships in this fork: `server/src/modules/workflows/` has the module wiring, five controllers, entities and migrations (`workflow_executions`, `workflow_execution_nodes/edges`, `workflow_schedules`, `workflow_bundles`), BullMQ queue config and processors, and the ability module (`ability/app/`). The execution logic itself is missing: 14 files (services, processors, controllers) are stubs that throw `Method not implemented` (the bundles controller throws `Enterprise feature` instead), `ability/app/index.ts`'s `defineAbilityFor` is a no-op `return;`, and the controllers carry only authentication-level guards (`JwtAuthGuard`, plus licensing's `WorkflowCountGuard` on the create endpoint) — no CASL `FeatureAbilityGuard` is wired anywhere under `modules/workflows/controllers/`, even though `ability/app/guard.ts` already defines one. The frontend scaffolding (`frontend/src/modules/workflows/`, `frontend/src/WorkflowEditor/`, `frontend/src/modules/RenderWorkflow/`) is minimal; the editor itself is greenfield work on `reactflow@^11.7.4`.

A behavioral reference exists: the extracted EE production build at `ee-extract/server-dist-ee/workflows/` — plain `tsc` output (`.js` with intact class/method names, plus `.d.ts` signatures) — is readable, unlike the original private EE repo. The directory is already gitignored (`/ee-extract/` in `.gitignore`).

The alternative shapes were: (a) leave Workflows EE-only (defeats the purpose of the fork for its owner); (b) port the EE dist files verbatim into CE (fast, but imports private-EE module paths like `@licensing/*`, drags license-gate logic into CE code, and imports code style the fork does not own); (c) reimplement from scratch with no reference (slow and needlessly divergent where the EE behavior is known-good).

## Decision

**The CE fork fully implements Workflows with no edition or license gating.** Every workflow capability — workflow apps, editor, server-side execution engine, manual and webhook triggers, schedules, run history (executions, node/edge state, logs, SSE streaming, terminate), AI agent node, Python executor, JS/Python dependency bundles — ships as CE code, runnable by any user of the fork regardless of license state. No `Enterprise feature` errors, plan checks, or feature flags gate it.

**Method: port-by-reference, not port-by-copy.** The 14 stub files are filled by reimplementing the behavior observable in `ee-extract/server-dist-ee/workflows/` as first-class CE code in this repo's style (NestJS module/controller/service/repository conventions, `src/`/`@modules/` path aliases, fork naming). The dist is a read-only behavioral reference — its method names, ordering, status mapping, and edge-case handling inform the implementation, but its code is not copied wholesale and its EE-only dependencies (`LicenseTermsService`, `@licensing/*`) are replaced with CE equivalents or removed where they only enforce gating. The `ee-extract/` directory stays gitignored and is never committed; losing it must not break the build or tests.

**Licensing risk, accepted explicitly.** The EE dist is proprietary upstream code; the AGPL that covers this fork's CE code does not cover it. Using it as a reference for a behavioral reimplementation is a fork-owner decision taken with the fork's private, non-distributed deployment in mind. This ADR records that acceptance; the mitigation is the reimplementation-not-copy rule above, which keeps committed CE code authored in this repo.

**Guards and permissions.** Every workflow controller endpoint gets `@UseGuards(JwtAuthGuard, FeatureAbilityGuard)` (the module-local `ability/app/guard.ts` guard), and `defineAbilityFor` in `ability/app/index.ts` gets real CASL rules replacing the no-op. The licensing `WorkflowCountGuard` on workflow creation is dropped — the fork policy is "no limits" (see below). Acceptance is enforced by the existing DB-backed specs (`server/test/modules/workflows/e2e/workflow-executions.spec.ts`, `workflow-webhook.spec.ts`, `workflow-bundles.spec.ts`, adapted to fork policy, plus unit `workflow-packages-ability.spec.ts`) turning green in WP-2/3/5, and by `grep -rn "Method not implemented\|Enterprise feature" server/src/modules/workflows/` returning empty.

**Engine configuration contract.** The execution engine is configured by environment variables, with these names fixed so tests and deployment agree: `WORKFLOW_TIMEOUT_SECONDS` (default 60 — already consumed by `constants/queue-config.ts`), `WORKFLOW_JS_MEMORY_LIMIT_MB` (isolated-vm (`ivm`) V8 isolate memory cap, default 20 — already consumed by `server/lib/utils.ts`), and `TOOLJET_WORKFLOW_SANDBOX_BYPASS` (selects the Python executor's `BYPASSED` sandbox mode; `SecurityModeDetectorService` currently hardcodes `BYPASSED` and will honor the variable when nsjail support lands).

## Consequences

- **The acceptance suites cited in the Decision do not run yet.** As of this ADR, all four of them — e2e `workflow-executions.spec.ts`, `workflow-webhook.spec.ts`, `workflow-bundles.spec.ts` and unit `workflow-packages-ability.spec.ts` — fail at module load: the e2e jest config (`test/jest-e2e.config.ts`) lacks the CE stub mappings for `@ee/audit-logs/module` (they exist only in the unit and AI-unit jest configs), and the unit spec imports `@ee/workflows/*` directly from the empty submodule. Closing that gap (e2e `moduleNameMapper` stubs and re-pointing the unit-spec imports to `src/modules/workflows/*`) is a precondition of the execution-engine work (WP-2). The DB-backed test contour is also locked to Node 22.15.1 until `isolated-vm` ships a prebuild for the Node 24 ABI (127 vs 137) — the dev toolchain stays on Node 24, the test contour runs Node 22.15.1 via the nvm path; baseline evidence is in the local plan tracker's "Baseline (WP-0, 2026-09-02)" section (untracked by design).
- **The editor is the largest single risk.** Roughly 3–4k lines of greenfield React (reactflow 11, which is pre-`@xyflow` and unmaintained upstream) on top of a minimal scaffold; it is phased (WP-1/4/6) rather than landed in one piece, and pinned at reactflow 11 until the ADR-0046 upstream merge is resolved.
- **nsjail may be absent** on hosts where the fork runs; the Python executor must degrade gracefully to `BYPASSED` mode (documented, less isolated) rather than fail workflow runs. The sandbox security tests encode both modes.
- **Existing e2e fixtures encode EE behavior** — rate limits and plan limits in `server/test/__fixtures__/workflow-*` — that the fork does not want. They are replaced with the fork policy "no limits" during WP-5; until then the bundles spec fails by design.
- **Upstream merge (ADR-0046) is still pending**, so the deployed container rebuild is deferred: shipping this feature set before absorbing upstream would repeat the regression ADR-0046 exists to prevent.
- Run history and schedules depend on Postgres and Redis (BullMQ) being present in every deployment of the fork — already true for the rest of ToolJet, but now a harder requirement, not an optional scaling nicety.
- If upstream later open-sources its workflows implementation, the CE code here remains the fork's own; divergence is expected and acceptable, since the fork's contract is the adapted acceptance specs, not upstream's source.
