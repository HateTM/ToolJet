# `CreateTable` may target a connected PostgreSQL source, gated behind explicit confirmation; every other kind stays excluded

ADR-0018 decided "never a place tables get created: only ToolJet DB receives a `CreateTable`" and rejected extending `CreateTable` to arbitrary data sources on the grounds that DDL capability is not uniform across connectors — "not one feature but a per-plugin matrix." That objection holds for arbitrary connectors. It does not hold for one: PostgreSQL is the dialect ToolJet DB itself already speaks, so `executeCreateTableStep`'s column-to-DDL translation needs a target connection swapped in, not a second translation written. This ADR narrows ADR-0018's prohibition from all external sources to all except PostgreSQL, and does not reopen the rejected general case — MySQL, MSSQL, Mongo, and everything else stay exactly as excluded as they were.

## Decided

A `CreateTable` step may target a connected `postgresql` data source in addition to ToolJet DB. Selection reuses the source picker introduced by ADR-0019 — the same enumerated, permission-filtered, schema-introspected list a `CreateQuery` step already chooses from — with one addition: when the selected source's kind is `postgresql`, the planner may propose `CreateTable` steps against it instead of being told, as ADR-0018 required, that none are available. Every other kind keeps the ADR-0018 behavior unchanged: no `CreateTable`, existing-schema-only.

**Name collision is a hard failure, decided at plan time, never at execution.** The same `listTables` introspection ADR-0019 already runs to populate the query picker is consulted for the proposed table name before the step is offered to the user. If a table by that name already exists in the target source, the step is not built — the plan surfaces it as an unbuildable proposal (the same retryable-guard shape `data_source_id`, `pageId`, and `queryName` already get) rather than attempting the table and failing mid-run, or worse, silently reusing someone else's table. Nothing about this feature ever issues `ALTER` or writes into a pre-existing table. A collision is not something to resolve; it is the sentinel value for "this can't be built" — because unlike ToolJet DB, where a table is disposable and app-scoped, a PostgreSQL source arrived over a connection that likely predates this app and outlives it.

**Execution requires an explicit, per-step confirmation that no other step in the plan requires.** Every step ADR-0004 through ADR-0024 describe runs unattended once a PRD is approved — `CreateTable` against ToolJet DB, `CreateQuery` against anything, `CreateComponent` — because none of them can do anything to data the user did not just finish being told about, in a place they did not just finish being told about it. A `CreateTable` step targeting an external PostgreSQL source is the first step in this system capable of running DDL, and then writing planner-proposed seed rows (ADR-0024's existing mechanism, unchanged, reused verbatim) into infrastructure the user owns outside ToolJet and did not create for this build. Execution reaching such a step pauses; the run UI shows exactly what will be created (the table name, its columns, the target connection, and the row count if seeding) and requires the user's explicit go-ahead before the DDL is issued. This is not the checkpoint-based `Skip` of ADR-0021 — skip declines to build a step; this is a second, narrower gate that stands only in front of the one step whose write lands somewhere ToolJet does not own. A rewind (ADR-0008) still undoes it afterward like any other Artifact; the confirmation is about the moment before the write, not a replacement for undo after it.

## Rejected

**Cover the whole SQL family (MySQL, MSSQL) alongside PostgreSQL, matching `CreateQuery`'s scope from ADR-0019.** `CreateQuery`'s SQL family works as one feature because every member takes a query as one `{ mode: 'sql', query }` string — one prompt, one tool schema, one validation path, regardless of dialect underneath. `CreateTable` has no equivalent uniformity: DDL syntax, type mapping, and constraint support diverge dialect to dialect in ways a single string cannot paper over. PostgreSQL is not "SQL-family, pick one" — it is the one dialect this codebase already generates DDL for, because ToolJet DB is Postgres. Extending to MySQL or MSSQL is a second translation this ADR does not write; ADR-0018's "per-plugin matrix" objection re-applies to that extension exactly as written.

**Cover Mongo (EE's other seedable kind) via a schemaless implicit-create path.** EE creates no explicit table for Mongo — a collection materializes on first insert, so seeding is a plain write with no DDL step in front of it. That is a different mechanism from everything else in this system, which is planned, previewed, and confirmed *before* anything is written (ADR-0020's schema preview exists specifically so the "Planned table" a user sees is what gets built, verbatim, with no further model call). Folding Mongo in means the plan can contain a step with no schema to preview and nothing to confirm the shape of — only that a write is about to happen. That is a real, separate feature, not a variant of this one.

**Allow seeding into an existing external table without `CreateTable`** — the narrower, non-DDL option this ADR's predecessor conversation first considered. Rejected for the same reason the hard-collision-failure rule above exists: a `CreateQuery`-shaped write into a table the user did not create for this build, chosen because a name happened to match, is exactly the "quietly running model-written SQL against production data" ADR-0019 already refused to do — except as an `INSERT` instead of a `SELECT`, which makes it worse, not better. If a use case for writing into an already-existing external table appears, it needs its own confirmation story; it does not fall out of this one.

## What this leaves for implementation

- `AgentsService.CreateTable`'s TJDB-only delegation (`TooljetDbTableOperationsService.perform(...)`) gains a second branch keyed on the selected source's kind, mirroring the `dataSourceId`-optional pattern `CreateQuery` already uses (ADR-0019) rather than a new step type — `StepType` stays `'CreateTable' | 'CreateQuery' | 'CreateComponent'`.
- The planner prompt and the `CreateTable` tool schema need the `postgresql`-vs-ToolJetDB distinction stated as plainly as ADR-0018 required the query prompt to state "no external tables" — now conditional on the selected source's kind rather than unconditionally true.
- The confirmation gate is new execution-loop state, not a new `Step` status: it sits between `pending`/`running` and the DDL call itself, for `CreateTable` steps whose resolved target is external only. It should log and surface through the same run-UI channel `Skip` already uses (ADR-0021), not a parallel one.
- Collision detection reuses ADR-0019's `listTables` call verbatim — no new introspection code, only a new question asked of its result (does this name exist) alongside the existing one (what tables exist, for the query prompt).
